# Building Blocks

Every lab workflow reads the same kind of `rig.yml`, modelled by `open_rigs.rigs.lab_rig.LabRig`, and builds its rig from the pieces below, so each workflow keeps only its task. A rig is any combination of the lab's devices: each device instance is one **piece** (an include such as `SpinnakerCamera` for `Camera-Face`), a few **core** includes hold what no single device owns (configuration, the Ready gate, the clock, the camera triggers), and a **rig list** (`DomeHardware`, `BBoxHardware`) holds the pieces and core of a rig kind, so every workflow that runs on that kind (its tasks, its preflight) names the same parts once. A new rig made of the same devices in a new combination needs no new hardware code. This page lists each include: what it takes, what it gives and where it lives.

A new rig kind needs: its rig list and its taps include in `OpenRigs.Devices` (`<Kind>Hardware.bonsai`, `<Kind>HardwareTaps.bonsai`); an entry in `workflow_lint.RIG_LISTS` whose text is the start of the rig list's `Description`, since `package_include` finds an include in a built package by that text (`SIGNATURES`), so a reworded `Description` needs the entry changed with it; an entry file and a task file in the preflight workflow (`src\<kind>.bonsai`, `config\task-<kind>.yml`, and its tests' `KINDS` entry); and a `[[preflight.by_profile]]` entry for the rig's profile in the launching app's `calibrations.toml`.

## The rig model and its parts

`open_rigs.rigs.lab_rig.LabRig` (`src/open_rigs/rigs/lab_rig.py`) is the whole of a rig's `rig.yml`. Every part is optional: a rig's file lists the parts it has, each workflow takes the ones it drives, and a name a workflow asks for and does not find stops it at Start. `uv run regenerate-lab-rig` here writes its schema (`src/open_rigs/schemas/lab_rig.json`) and generates its C# into OpenRigs.Devices (`OpenRigs.Devices.Rigs`: `LabRig`, `DeserializeFromYaml`, `SerializeToJson`), which every lab workflow reads `rig.yml` with, so no workflow generates or keeps its own; `src/open_rigs/rigs/rig-template.yml` is the lab's one template, which a new rig's `rig.yml` is copied from. The parts are in `src/open_rigs/components/`:

| Part | `rig.yml` key | Module |
|---|---|---|
| Harp Behavior boards (`BehaviorBoard`, its `wiring` and `liveView`) | `behaviorBoard` | `harp_boards`, `wiring`, `live_view` |
| Timestamp generators | `timestampGeneratorGen3` | `open_rigs.devices` |
| Stepper drivers of a lick spout stage (`HarpStepperDriver`, its `wiring`) and the stage's default position | `stepperDriver`, `lickSpoutDefaultPosition` | `harp_boards`, `wiring` |
| Lick detectors | `licketySplit` | `open_rigs.devices` |
| Cameras (`SpinnakerCamera`: serial, `exposureUs`, `gainDb`, binning, `pixelFormat`, blank keeping the camera's stored format) and the machine's `VideoEncoder` | `camera`, `videoEncoder` | `video` |
| A projector's mesh and gamma table | `projector` | `projector` |
| Speakers, every one equalised, and the penalty sound's channel (`EqualisedSpeakerArray`) | `speakerArray` | `speakers` |
| Zapit (`ZapitServer`) | `zapit` | `zapit` |

Reward valves and the Zapit trigger are found from the Behavior board's `wiring`:

```yaml
behaviorBoard:
  main:
    portName: COM3
    usbSerial: AB0M7PLB
    pulseController:
      outputPulseEnable: "DO1, DO2"
      outputs:
        DO1: { discriminatorType: CalibratedPulse, artefact: calibration/RewardValve-Left.json }
        DO2: { discriminatorType: CalibratedPulse, artefact: calibration/RewardValve-Right.json }
        DO3: { discriminatorType: FixedPulse, pulseWidthMs: 0 }
    wiring:
      DO0: { device: CameraTrigger, targets: [Camera-Face, Camera-Pupil, Camera-Body] }
      DO1: { device: RewardValve, name: left }
      DO2: { device: RewardValve, name: right }
      DO3: { device: ZapitTrigger, note: also the masking light }
```

The model refuses a `rig.yml` whose wiring has a `RewardValve` without its `name` (its piece is `RewardValve-<Name>`: `name: left` is `RewardValve-Left`), two valves of one name anywhere on the rig, one on a line the board cannot pulse (DO0 to DO3 and DOPort0 to DOPort2 can), or one on a line whose output is not a `CalibratedPulse`; more than one `ZapitTrigger` on the rig, or one on a line in `outputPulseEnable` (a pulse-enabled line ends itself after its `PulseDOx` width, and the Zapit line, with the masking light on it, is held from the trigger until the workflow clears it; its `outputs` entry stays, a `FixedPulse` of width 0); a `zapit` section with no `ZapitTrigger` line; a `Photodiode` on a line that is not a digital input (`DIPort0` to `DIPort2`, `DI3`, `DIO0` to `DIO2`), or two on one board (`LabRig.photodiode_lines()` gives each board's; the Photodiode is one device, wired on `DIPort0` for the screen's sync square, and the projector's gamma calibration reads the same sensor on `ADC0`); and a camera that no DO0 or DO1 `CameraTrigger` line names in its `targets` (as `Camera-<Entry>`, the entry capitalised). It refuses any key it does not know, as the generated C# does at Start. Every refusal says what it refuses, "(lab rig model, open_rigs.rigs.lab_rig)", then how to fix it. A speaker array needs `penaltySoundChannel` (beside `device.bootDelaySeconds`, `syncChannel` and `syncGain`) and a filter on every speaker.

## A piece

Each piece is one device instance, named `Kind-Instance` as in the data (`Camera-Face`, `LicketySplit-Left`, `BehaviorBoard-Main`). It takes its entry from `rig.yml` (`RigConfigs`, from `ReadLabRig`) by that `Name`, publishes the entry as the `AsyncSubject` `<Name>`, opens the device behind `<Name>.Data` (a `PublishSubject`) and, for a device that takes commands, `<Name>.Commands` (a `BehaviorSubject`, so a per-trial graph that sends one command and completes leaves it open), and logs itself under `<Name>\` once the experiment folder exists (`PathPrefix`) and, for a Harp device, the Harp clock is set (`HarpClockSet`). Its `Name` is one externalised property, mapped onto every place inside that needs it (`RigDevice`, the subject, its log), so a piece cannot log under one name and open another. `CommandsSubjectName` and `DataSubjectName` stay explicit properties, as Bonsai's XML cannot build a string, and `workflow_lint` holds them equal to `<Name>.Commands` and `<Name>.Data`. A line piece on a Behavior board (`PulseOutputs`, `ZapitTriggerLine`, `RunningWheel`, `ClockFromBoard`, `SpinnakerCamera`, `CameraTriggers`) takes the board's `Name` as `Board`, and the board's subjects it uses, held equal the same way: `PulseOutputs`, `RunningWheel`, `ClockFromBoard` and `CameraTriggers` take `BoardCommandsSubjectName` and `BoardDataSubjectName`; `SpinnakerCamera` takes only `BoardDataSubjectName` (it has no commands property); `ZapitTriggerLine` takes only `Board`, `ManualPulses` `Board` and `BoardCommandsSubjectName`, and `CameraLiveControls` `Board` and `Camera`. A piece's `Name` starts with its kind (`BehaviorBoard-`, `Camera-`, `LicketySplit-`, `TimestampGeneratorGen3-`): `RigDevice` finds the entry by the instance alone in the piece's own `rig.yml` group. A piece's other inputs (`CamerasExpected`, `WheelDistanceSubjectName`, `Binning`, ...) are its own properties. `DomeHardware` and `BBoxHardware` are the worked examples of a rig list. Every name defaults empty or `UNMAPPED`, never a real subject's name, so an unset one fails the build naming no other device's subject. A piece that needs to be ready before Go announces its stage into `ReadyStages` through Core's `AnnounceStage`, which never completes (a source that completed into the `ReplaySubject` would close it for every other piece). A piece missing from `rig.yml` stops the workflow at Start, naming the entries there are.

`rig.yml` configures pieces; it never adds or removes one. A workflow's graph is fixed in its XML, so a rig lacking a device its workflow includes cannot run it.

A workflow has exactly one clock. Order in the workflow: `ReadLabRig`, `ReadyGate`, then the clock and pieces in any order. Keep `ReadLabRig` where nothing it reads is defined later, ahead of the group that holds the pieces. The C# lookups by name (`ExperimentManifest`, `RecordHarpDevices`, `StreamDevices`) come after the pieces.

## The rig list

`DomeHardware` (`OpenRigs.Devices:DomeHardware.bonsai`) is the hardware of every rig of its kind: `ReadyGate`, `ClockFromTimestampGenerator` (`TimestampGeneratorGen3-Main`), `BehaviorBoard-Main` with `PulseOutputs`, `ZapitTriggerLine` and `RunningWheel` (`WheelDistanceCm`), `LicketySplit-Left` and `-Right` (`LickStateLeft`, `LickStateRight`), `LickSpoutStage`, `Camera-Face`, `Camera-Pupil`, `Camera-Body`, `CameraTriggers`, `SpeakerMixer` and `ProjectorDisplay` (from `rig.yml`'s `projector`): every task on these rigs has background noise and a screen. Its `ReadyGate` waits for every stage these announce, `MixerStarted` included. It exposes `DisplayDevice` and `WorkflowStages` (its `ReadyGate`'s). It holds no `ReadLabRig`: the workflow includes that once, before it, as a piece's log waits for `PathPrefix`, whose `ExperimentLogs` reads `RigConfigs`, so `RigConfigs` defined inside the rig list would be defined in terms of itself (`hardware_problems` refuses a `ReadLabRig` after `ReadyGate`). Every rig of that kind has these devices under these names. A task on it makes its own sounds and stimuli (multicast into the mixer's subjects, drawn on `DrawStimuli`) and includes neither again (`hardware_problems`); Zapit is the task's.

`BBoxHardware` (`OpenRigs.Devices:BBoxHardware.bonsai`) is the behaviour boxes' hardware: `ReadyGate` (waiting for `HarpClockSet` and `Camera-Overhead`), `BehaviorBoard-Main` with its own clock (`ClockFromBoard`) and `RunningWheel` (`WheelDistanceCm`), and `Camera-Overhead` on `CameraTriggers`. It exposes `Binning`, the camera's in place of `rig.yml`'s while set, and `WorkflowStages` (its `ReadyGate`'s). `CameraLiveControls`, optional, stays in the task that wants it.

A workflow that runs on several rig kinds is one thin entry file per kind and one shared include of its own: each entry (`src\<kind>.bonsai`) holds only its launch properties, `Initialization` (`ExperimentControl`), its kind's rig list and the shared include (such as `src\Extensions\Job.bonsai`), which holds the job, with `LiveView` its last top-level node. A stage the job announces itself (a valve calibration's `CalibrationReady`) is the entry's `WorkflowStages` on its rig list, which passes it to `ReadyGate`. `workflow_lint` reads each own include as the workflow (`Workflow` puts its nodes inside the include node), opening its `Path` as Bonsai 2.9 does: from the launched workflow's folder (`src`, Bonsai's working directory), never from the including file's, `.bonsai` added to a `Path` with none; an own include Bonsai would not find stops the lint naming it.

## Task-side includes

These hold what every task does the same way, but stay in the task: their inputs or files are the task's. A task includes `LaunchSettings`, `ExperimentLogs`, `BackgroundNoise` and `PlayPenaltySound` (with sound), `PlayPenaltyFlash` (with a projector), `TaskLogs`, `LogRngSeed`, `Rewards` (with reward valves, then one `RewardValve` per valve) and `ExperimentRecords` once each; `LogControlEvents` is inside `ExperimentRecords`, `LogTrials` and `ZapitLogs` inside `TaskLogs`. Reading the task file stays in each task, as its type is the task's.

### A workflow with no experiment folder

A calibration or a preflight drives the same pieces but makes no experiment folder. It includes `NoExperimentFolder` (`OpenRigs.Logging:NoExperimentFolder.bonsai`) once, in place of both `LaunchSettings` and `ExperimentLogs`. Its `SubjectId` is its own `_no-experiment_` (`workflow_lint.NO_EXPERIMENT_SUBJECT`), a name that is no mouse's, which a workflow may not set. It gives what the pieces read from an experiment: `PathPrefix`, declared and never published, so no piece's log starts and nothing is written under `rig.yml`'s `rootPath`; and `SubjectId` from Start, so `LickSpoutStage`'s in positions are `rig.yml`'s `lickSpoutDefaultPosition` and `SaveSpoutPositions` writes no row; and `Events`, declared and never written, for the events a piece sends. The workflow writes only its own files (a calibration's results beside `rig.yml`). `no_experiment_folder_problems` holds every workflow to one of `ExperimentLogs` and `NoExperimentFolder`, once, and refuses its own stand-ins: a `PathPrefix` it declares or publishes, and, with `NoExperimentFolder`, `LaunchSettings` or a `SubjectId` of its own, in its own included files too.

### A preflight

A preflight checks every device a rig's `rig.yml` declares before training, one workflow per rig kind: its rig list, `NoExperimentFolder`, and `PreflightChecks` (`OpenRigs.Devices:PreflightChecks.bonsai`), the check every kind shares, with no device code of its own. Its rows are `rig.yml`'s devices (`PreflightDevices`, in the order `behaviorBoard`, `timestampGeneratorGen3`, `stepperDriver`, `licketySplit`, `camera`, `speakerArray`, `projector`), so a device `rig.yml` has and the rig list lacks still has a row, an error. Its rig list's taps include (`OpenRigs.Devices:DomeHardwareTaps.bonsai`, `BBoxHardwareTaps.bonsai`, after `PreflightChecks`) taps each piece's `<Name>.Data`, and `DomeHardware`'s projector frames (`DrawStimuli`, as `Projector`), through `PreflightTap` into `DeviceTicks`, which `PreflightChecks` declares, so the preflight names no device itself (`workflow_lint.preflight_tap_problems`): a tick per item, counted each second; a device that has sent nothing 5 s after start has its error until its first item (`DeviceReports`) into the `devices` metric (`DeviceRates`). A fault beyond presence (a port another program holds, a camera that sends no frame, a clock never set) stops the preflight at Start naming the device, as the piece stops a task. At Go `PreflightChecks` reads its property `TaskPath`, the rig kind's task file (`ReadPreflightTask`: `countSeconds`, 1 to 60, and `questions` by `rig.yml` kind; any other key is refused), counts each device in turn (`step` metric), asks each question in turn (`prompt` metric) until the controller's `Confirm` (`PreflightChecks` declares it, and passes each on `Confirms` for the workflow's own use, such as playing a test sound until it is answered), writes the rows (`device,measure,value,detail`) to its property `RawFile` and reports `Finished`. A speaker array has no count: the workflow multicasts the test sounds it sent into `SpeakerSounds`, given before the person's answer.

A piece declares its own commands and parameters with OpenRigs.Control's `DeclareControls` (`Piece`, `Parameters`, `Commands`, as `ExperimentControl`'s): `ControlServer` gathers every piece's subscribed before or after it, so `status` lists them with the piece's name (`piece`, empty for the task's own) and a name declared twice (a task's copy, a piece included twice) stops the workflow at Start naming both. A piece the workflow does not include, or that does not run on this rig (a stage behind a condition that finds none in rig.yml), declares nothing. `ExperimentControl`'s `Parameters` and `Commands` are the task's own. `workflow_lint.control_declarations` reads both inside every include it can (a declaring piece is in `SIGNATURES`), held by `undeclared_commands`, `declared_twice` and `spout_step_size_problems`. A piece included once per device declares its controls named from the device with `DeclareDeviceControls` (`Name` the device, the piece; each parameter and command `<Name>.<its name>`), and reads them with `OnDeviceParameterSet`, `DeviceParameterDefault` and `DeviceParameterMaximum` (`Name`, `Parameter`), so one externalized `Name` names the device, its subjects and its controls: `CameraLiveControls` declares `<Camera>.ExposureUs` and `<Camera>.GainDb`, and `workflow_lint` (`DEVICE_DECLARERS`) reads them per include and refuses two on one camera. OpenRigs.Control's `EndAfterStop` (beside `ExperimentControl`) ends headless Bonsai when it is still running `GraceSeconds` (2) after the controller's stop, exit code 0, or after the workflow began to end with no stop, an error, exit code 1 (headless Bonsai exits 0 after an error); nothing in the editor. `ExperimentManifest`'s `ConfigFiles` defaults to `{RigFiles}`: `rig.yml` under its `ConfigRoot` (from `ExperimentRecords`), and every path-like value in it; on a rig with `lickSpoutDefaultPosition` the manifest records the mouse's five spout positions as numbers (`spout_positions`).

## Ready

`ReadyGate` reports `Ready`, which lets the operator press Go, once every stage in its `PieceStages` and `WorkflowStages` has come into `ReadyStages`. `PieceStages` is the stages the workflow's pieces announce: `HarpClockSet` (the clock; `HarpClockRead` for a `ClockFromBoard` with `SetClock` false), `SpoutsHomed` (`LickSpoutStage`), each camera's `Name` at its first frame, and `MixerStarted` (`SpeakerMixer`, at least 3 s after Start), so every sound a task sends from Ready on is played. A workflow that needs more before Go announces a stage of its own (an `AnnounceStage` into `ReadyStages`) and names it in `WorkflowStages`: the valve calibration's `CalibrationReady` (its pulse setup out and the spouts in), the projector calibration's `CalibrationReady` (the first ADC0 reading). A workflow with `ExperimentLogs` also includes `LabClockReady` after its hardware and names its `LabClockChecked` there: it checks the clock against `lab.yml` at Start (`LabClockAgrees`), so a clock fault stops the workflow before Ready, not at Go. It is a `WorkflowStages` entry because a rig list's `PieceStages` is fixed and also serves workflows that record nothing, and its own include because `ExperimentLogs`, before the hardware, announcing into `ReadyStages` would make Bonsai build the hardware in terms of itself. `workflow_lint.hardware_problems` holds `PieceStages` equal to the stages the workflow's pieces announce and `WorkflowStages` to those the workflow announces itself (with `LabClockReady`'s `LabClockChecked`), and refuses any multicast into `ReadyStages` not fed by one `AnnounceStage`, reading the workflow's own included files (`src\Extensions`) as the workflow. A piece behind a per-element operator (a `SelectMany` that runs it only on a rig whose `rig.yml` has its device, as the valve calibration's lick spout stage) may never announce, so `PieceStages` leaves its stage out and the workflow waits with a stage of its own. `CheckMixerStarted` stays the safety net: a stimulus or penalty sound that still reaches the mixer before it has started stops the workflow.

## Sound

Every sound a task plays goes through `OpenRigs.Audio` ([Speakers and Sounds](../bonsai-operators/OpenRigs.Audio/speakers.md)). `SpeakerMixer` loads the speakers (`Speakers`) and starts the mixer; a task makes each sound's buffer and multicasts it into the mixer's subject for it. `SpeakerBuffer` lays a sound (or a table of sounds) out on chosen speakers, equalised for each (a stimulus) or not (a background noise); its `SyncCopy` adds a stimulus's sync copy (`syncGain` on `syncChannel` for the sound's length), so acquisition sees when every stimulus plays; `PenaltySoundBuffer` gives the lab's one penalty sound on `penaltySoundChannel` alone, so a task file names no penalty sound file; `BackgroundNoise` plays the lab's one background noise, the file `rig.yml`'s `speakerArray.backgroundNoise` names (the server's `config\shared\sounds\background_noise.wav`, copied to each rig by its upkeep), so no task keeps a noise file.

Every sound plays at a level, never a gain: `levelDbfs` in the task file, in dBFS RMS, the RMS of the sound over its samples outside silent stretches (runs of exactly-zero samples at least 1 ms long), as the task gives it (before equalisation) against full scale, so a full-scale sine is -3 dBFS (`SoundLevel`, which takes the sound's sample rate), or `mute` for no sound (`OpenRigs.Trials` `SoundLevels.Parse`, NaN). A level that varies by trial is condition-level: the buffer is laid out at Go at the highest level any trial draws (`MaxSoundLevel.Of`) and each play scaled to its trial's (`SoundAtLevel`), as `PlayPenaltySound` and `PlayRewardTone` do; one buffer for several levels takes the highest of them all (`MaxSoundLevel.Of(conditions, t => t.Penalty.Incorrect.Sound.LevelDbfs, t => t.Penalty.NoResponse == null ? null : t.Penalty.NoResponse.Sound.LevelDbfs)`, a null skipped). `open_rigs.core.task` holds the task file's blocks (`Reward` with its `tone`, `Penalty`, a conditioned task's `AuditoryStimulus`) and the lab's defaults, the same as `SoundLevel`'s: stimuli -30, penalty -35, reward tone `mute`; the background noise is the lab's -60, no task setting. They are defaults only: each task file states its levels. A buffer whose peak reaches -1 dBFS after equalisation stops the workflow, naming the sound and how far to lower it; build each buffer at Go, so the check comes before trial 1. No task scales a sound itself. The levels become dB SPL once each speaker is calibrated for loudness.

A task's `penalty` block (`open_rigs.core.task` `Penalty`) is what a penalised trial costs, by its kind, each kind its own full values and nothing inherited: `incorrect` (a wrong choice, a go/no-go false alarm, a probe's tails) and `noResponse` (a miss), each `{timeoutSeconds, sound: {levelDbfs}}`, defaults 4 s and -35 dBFS. `noResponse` may be null: misses are never penalised (go/no-go), and a task that penalises a miss refuses that at Go (`Penalties.Problems(missesPenalised, hasNoResponse)`, `Penalty.check_misses` in Python). Which trials are penalised, and of which kind, is the task's: it passes the kind to `OpenRigs.Trials` `Penalties.For(kind, incorrectTimeoutSeconds, incorrectLevelDbfs, noResponseTimeoutSeconds, noResponseLevelDbfs)` (`PenaltyKind.Incorrect` or `NoResponse`; the noResponse values null when the block is), which gives the trial's `TimeoutSeconds` (logged as `penaltyTimeoutSeconds`) and `LevelDbfs` (NaN when mute). The `reward` block (`Reward`) holds `sizeUl`, `largeMultiplier`, `largeProbability` and `tone: {levelDbfs}` (default `mute`); a reward delays nothing (the time to drink it is the spouts' `rewardConsumptionSeconds`, inside the interval).

## The trial loop

Every task runs its trials on `TrialLoop` (OpenRigs.Trials), so the trial start, the laser's lead and trigger, the response window and the interval are timed one way in every task ([Trial Loop](../bonsai-operators/OpenRigs.Trials/trial-loop.md)). A trial: drawn at its interval's start (the last outcome plus its timeout when penalised, `ITrialOutcome.PenaltyTimeoutSeconds`, else the outcome itself; trial 1 the first tick); a hardware-triggered Zapit armed during the interval once the last laser is done; the start at the interval's end less the lead, `max(laserToStimulusSeconds, 0)`, or later until the quiet waits hold (`QuietWait`); the trigger `laserToStimulusSeconds` before the stimulus, stopping the workflow if Zapit has not armed the trial by then (naming the last laser when it held Zapit past the trigger, or freed it less than the 0.2 s reply margin before it; without hardware triggering, a trigger before the last laser frees Zapit stops it the same way), and never on a trial already answered; the stimulus the lead after the start; the response window `ResponseDelaySeconds` after the stimulus for `ResponseWindowSeconds`; the outcome, then its timeout. The task supplies the rest as an `ITrialRules`: the draw (given the last outcome), each trial's `TrialTiming` (`ItiSeconds`, lead, quiet waits, laser, response window, `TrialCue`s: from the stimulus or the next interval's start (`CueAnchor.Stimulus`, `NextIti`), a stimulus cue `droppedAtOutcome` never coming once the trial has its outcome, such as the spouts in), and the response rule, called at the start, the stimulus, each tick from the stimulus, each lick, each wheel sample and the window's end, returning the outcome when the trial ends. `LaserTiming.UntilOutcome` keeps the laser on to the outcome (stopped at `LaserCap`) with the trigger line held past it; `LaserTiming.ForDuration` runs it a fixed time from the trigger, the next trial armed after Zapit's ramp-down. A trial is an `ITrial` (its `TrialNumber`), and an `IZapitTrial` (its laser condition, laser on and power) only in a task whose trials are laser trials; an outcome is a `TrialOutcome<TRow>` (an `ITrialOutcome`), built from the filled row and the rewarded valve's `rig.yml` wiring name (`left`): `Row` stamped with `outcomeTime`, `Rewarded`, `Reward` (null unless rewarded), `Penalised`, `PenaltyLevelDbfs` (NaN when mute), `PenaltyTimeoutSeconds`, its row's `outcome` one of `TrialOutcomes` (`correct`, `incorrect`, `noResponse`, `probe`, held equal to `OUTCOMES`); a task whose outcome sets off more (its spouts) derives from it. The loop takes one lick input per spout (spout 0 the first) and the wheel only on a rig with one; the clock ending ends the trials, a lick input or the wheel ending stops them naming it. The names are the trial columns': `TrialTimes.ItiStartTime`, `ItiSeconds`, the `Iti` event at the interval's start.

A task's `src\Extensions` declares its rules and a three-line `RunTrials` combinator that returns `TrialLoop.Observe` on its streams; its `TaskLogic` multicasts the events into `TrialEvents` and picks each kind with `PickTrialEvents` to drive the hardware: `Trial` from `Start`, the trigger line from `Trigger` and `TriggerOff`, and each `Outcome` into `OpenRigs.Trials:TrialOutcomeEffects` (a rewarded outcome's reward into `RewardRequests` first, then its row into `TrialRow` once the valve's `RewardDelivered` has come for it, `rewarded` (`RewardedAsDelivered`; not rewarded when the next outcome comes first, and no row when the stop comes first), a penalised one's penalty sound at its `PenaltyLevelDbfs`), then into `OpenRigs.Vision:PlayPenaltyFlash` on a rig with a projector (its `PenaltyFlash`). The row's shared block is filled by `SharedTrialColumns.Fill(row, trial, times, rewardOfferedUl, rewarded, penalised, penaltyTimeoutSeconds, penaltyFlashBrightness)` from the loop's `TrialTimes` and the outcome: `trialNumber`, `itiStartTime`, `itiSeconds`, `quietWaitSeconds` (if the row has it), `trialStartTime`, `stimulusOnsetTime`, `stimulusOffTime` (`TrialTimes.StimulusOffTime`), `outcomeTime`, `rewardOfferedUl` (the offer, on every trial), `rewarded` (the value the task's reward command is made from), `penaltyTimeoutSeconds`, `penaltyFlashBrightness` (the kind's `flash.brightness` when penalised, else 0), `penalised` and the optogenetics block (`laserCondition`, `laserPointsMm` its points (`IZapitTrial.LaserPointsMm`, empty at condition 0), `laserPowerMw` 0 unless the laser was triggered, `laserTriggerTime`), by field name, refusing a row missing or mistyping one; the task fills `trialType`, `outcome` and its own columns.

A task whose spouts move holds the lab's `spouts` block (`open_rigs.core.task` `Spouts`: `alwaysIn`, `stimulusToSpoutsInSeconds`, signed like `laserToStimulusSeconds`, `rewardConsumptionSeconds`, default 1.5) and moves them with `OpenRigs.Trials` `SpoutCommands` on its trial events into `LickSpoutStage`: both out at trial 1's interval start, its trial's `SpoutsInCommand` at the `SpoutsIn` cue (before the stimulus when `stimulusToSpoutsInSeconds` is negative: a negative `Stimulus` cue leads the trial start, `TrialLoop.Lead` = max(`laserToStimulusSeconds`, the earliest cue's lead, 0), and the quiet waits hold it as they hold the laser's lead), at the outcome the rewarded valve's spout alone (`TrialOutcome.SpoutCommand`, `Spouts.AtOutcome`) or both out, and both out at the `SpoutsOut` cue, `rewardConsumptionSeconds` into the next interval (time to drink a reward; the interval never waits for it), unless the coming trial's are always in; a trial whose spouts are always in moves only at `SpoutsIn` and leads nothing (its negative `stimulusToSpoutsInSeconds` counts as 0, so it starts as it would without spouts). Its trial is an `ISpoutTrial` (`SpoutsAlwaysIn`, `SpoutsInCommand`, the task's choice of both or one spout), its `TrialTiming.Cues` take `Spouts.Cues(stimulusToSpoutsInSeconds, alwaysIn, rewardConsumptionSeconds)`, and its Go check adds `Spouts.Problems(stimulusToSpoutsInSeconds, alwaysIn, rewardConsumptionSeconds, itiMinSeconds, stimulusToResponseWindowSeconds)` per combination (`rewardConsumptionSeconds` at most `itiMinSeconds`, and plus the spouts' lead at most `itiMinSeconds`: they go out before they come back in; `Spouts.check_fits` in Python) and `Spouts.BetweenTrialsProblems(stimulusToSpoutsInSeconds, alwaysIn, rewardConsumptionSeconds, itiMinSeconds)` across the weighted ones. The lab's usual interval, `itiMinSeconds` 2.5 and `itiMaxSeconds` 3.5, holds the default 1.5 s and a lead up to 1 s.

The spouts block's `biasCorrection` (`open_rigs.core.task` `BiasCorrection`: `enabled`, default false; `trialsPerSide`, default 10, at least 1; `threshold`, default 0.3, above 0 and at most 1; `stepSteps`, default 100, at least 1 and at most `maxSteps`; `maxSteps`, default 500, 1 to 1000, `BIAS_CORRECTION_MAX_STEPS`) moves the spouts sideways toward the side the mouse neglects. It is one value per experiment: a conditioned task with spouts adds `conditioned_task.SPOUTS_SESSION_FIELDS` (`spouts.biasCorrection`) to its `SESSION_FIELDS`, so no trial condition sets it. With it on, the task makes one `OpenRigs.Trials` `SpoutBias(trialsPerSide, threshold, stepSteps, maxSteps)` per experiment, sends its `StageSettings` once to `LickSpoutStage.BiasSettings`, and at each outcome sets the outcome's `SpoutBiasCommand` (`TrialOutcome`, an `ISpoutBiasOutcome`) to `SpoutBias.Respond` of the finished trial, an `ISpoutBiasResponse` (`Target`, `Choice`, `SingleSpoutOffered`, `RepeatCount`, `LaserOn`). `Respond` counts a trial with a left or right target, both spouts offered, a left or right choice, no repeat and the laser off into its side's buffer of the last `trialsPerSide` results (correct: the choice is the target); once both are full, after every counted response, the left fraction correct less the right's above `threshold` gives `BiasLeft` (the base toward the mouse's left, the right spout toward the midline), below minus `threshold` `BiasRight`, else nothing (the offset stays where the mouse is balanced), at most one move a trial and none past `maxSteps` (`OffsetSteps` is the offset so far, as the stage holds it). `SpoutCommands` sends the move after the outcome's own move on an unrewarded trial, and on a rewarded one at the `SpoutsOut` cue, after that cue's own move, with always-in spouts too, so the spout never shifts while the mouse drinks; an outcome with no bias move leaves the stream as it was. The task's Go check adds `SpoutBias.Problems(trialsPerSide, threshold, stepSteps, maxSteps)`, and refuses `enabled` on a task with one spout itself.

A choice ends the trial unless the task keeps the response window always full (`open_rigs.core.task` `ResponseWindowAlwaysFull`, a block a task adds beside `ResponseWindow`: `responseWindowAlwaysFull`, true by default in a task that has the block; a task without it, and `TrialTiming` itself, default to a choice ending the trial). With it the trial's `TrialTiming` sets `ResponseWindowAlwaysFull` true. The outcome still comes at the choice with everything it sets off (the row, the reward, the spouts, the penalty sound and flash, the laser's end, the stimulus off and the dropped cues), and later licks are not the rules'; but the trial ends at the window's end, rewarded or not (`TrialTimes.TrialEndTime`), and the next interval starts there, after a penalised trial's timeout (a miss is timed as before). The drink is unchanged: `SpoutsOut` still comes `rewardConsumptionSeconds` into that interval, and the spouts' checks are the same. Its row has the `trialEnd` block.

When the stimulus ends is the lab's `stimulus` timing (`open_rigs.core.task` `StimulusTiming`, which a task's stimulus model inherits: `durationSeconds`, the longest it lasts from onset, null for no cap; `responseToStimulusOffSeconds`, null for a response that does not end it, 0 for off at the response, X for X s after it; the response is the outcome, on a miss the response window's end): off at the earlier of onset plus `durationSeconds` (both null is refused at Go; in the loop it means no off is timed) and the outcome plus `responseToStimulusOffSeconds` (`StimulusTiming.Time`). A task gives both in its `TrialTiming` (`StimulusDurationSeconds`, NaN for null; `ResponseToStimulusOffSeconds`; NaN and null by default, no off timed), and the loop emits one `StimulusOff` event per trial whose stimulus came on, at the first tick at or after that time (at the outcome itself when the time is the outcome): its workflow picks it with `PickTrialEvents` Kind `StimulusOff` to stop the stimulus sounds and hide its visual stimulus. `TrialTimes.StimulusOffTime` is the row's `stimulusOffTime`. Rules that are an `IStimulusAfterOutcome` keep updating the stimulus after the outcome (`AfterOutcome(trial, times, wheelCm, updates)`, each clock tick and wheel input, as Update events of that trial) until its `StimulusOff` or the next trial's start. Its Go check adds `StimulusTiming.Problems` per combination (the stimulus off before the soonest next stimulus: the duration within the stimulus to the soonest outcome plus the shortest outcome to next interval (the shortest penalty timeout, 0 where a trial can be rewarded or neither) plus `itiMinSeconds`, and within the response window; `responseToStimulusOffSeconds` within that shortest outcome to next interval plus `itiMinSeconds`; the next trial's lead moves its start, never its stimulus) and `StimulusTiming.BetweenTrialsProblems` across the weighted ones (`StimulusTiming.check_fits` in Python).

## The trial log

Every task's `schemas\trial-columns.yml` starts with the shared block, in order, with the same types, units and descriptions: the lab's 15 core columns `harpTime, trialNumber, trialType, outcome, itiStartTime, itiSeconds, trialStartTime, stimulusOnsetTime, stimulusOffTime, outcomeTime, rewardOfferedUl, rewarded, penaltyTimeoutSeconds, penaltyFlashBrightness, penalised` (`trialType` and `outcome` described by each task, and which outcomes are rewarded or penalised in each task's note), with each opt-in block the task uses in its place: `quietWait` (`quietWaitSeconds`, after `itiSeconds`), `trialEnd` (`trialEndTime`, after `outcomeTime`: where the trial ended and its timeout began, the next interval starting at it plus `penaltyTimeoutSeconds`; a task whose response window always runs in full must have it), then after `penalised` `optogenetics` (`laserCondition, laserPointsMm, laserPowerMw, laserTriggerTime`) and a conditioned task's `conditions`, `stimulus` and `autoReward`. The blocks are `open_rigs.rigs.trials`' `CORE_COLUMNS` and `BLOCKS`; each task's `tests\test_trial_columns.py` holds its file to them with `shared_block_problems(columns, blocks)`, naming the blocks it uses, so change a block there and regenerate every task's file. A task's own columns follow.

Keep a task's outcome logic (what counts as the response, and the reward, penalty sound and spouts that follow) in one C# operator that runs on every tick, the way a corridor task's state machine runs on every position update. Nodes that run only at an outcome pay .NET's first-run compile at trial 1's: in a two-spout task whose choice, row and consequence are a chain of nodes, trial 1's reward came 8 to 20 ms after its outcome and every later one within 2 ms; neither writing the row on its own thread nor compiling the task's C# at Start changed it, and only an earlier outcome through the same nodes did. `summarise-experiment` reports a reward more than 2 ms late.

`uv run summarise-experiment <experiment folder>` (`open_rigs.rigs.trials.summarise`) reads one experiment from its files alone and checks the rows against each other and the task file: trial numbers and outcomes, each trial's start, stimulus and laser trigger within 2 ms of where the task puts it, each interval starting at the last outcome (its `trialEndTime` where the log has one) plus its timeout, the timeout exactly on the `penalised` trials (the trial's combination's `penalty.incorrect.timeoutSeconds`, or on a miss its `penalty.noResponse.timeoutSeconds`; a miss is a `choice` of `noResponse`, or with no `choice` column an `outcome` of `noResponse`), and a `RewardDelivered` row requesting `rewardOfferedUl` at the outcome of each `rewarded` trial and of no other. A log without `quietWaitSeconds` has no quiet waits, and a task file without `optogenetics` no lead. Its performance is `performance()`'s: correct / (correct + incorrect) over the trials not offered a single spout (`singleSpoutOffered` false) and every go/no-go trial, a go trial with no lick counted incorrect.

## Video logging

Each `SpinnakerCamera` logs its own video with `OpenRigs.Logging:LogVideoFfmpeg.bonsai` as `<Name>` (`workflow_lint` refuses upstream's `LogVideo` and `LogRawVideo`, kept for upstream merges), at its trigger's frequency, from its first frame once `PathPrefix` exists. Every video and its CSV include the first frame, and a dropped frame is a jump in `frameId` with the triggers around it kept. A frame counter that goes back stops the workflow, naming the camera.
