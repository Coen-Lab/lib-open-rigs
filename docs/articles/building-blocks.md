# Building Blocks

Every lab workflow reads the same kind of `rig.yml`, modelled by `open_rigs.rigs.lab_rig.LabRig`, and builds its rig from the pieces below, so each workflow keeps only its task. A rig is any combination of the lab's devices: each device instance is one **piece** (an include such as `SpinnakerCamera` for `Camera-Face`), a few **core** includes hold what no single device owns (configuration, the Ready gate, the clock, the camera triggers), and a **rig list** (`DomeHardware`, `BehaviorBoxHardware`) holds the pieces and core of a rig kind, so every workflow that runs on that kind (its tasks, its preflight) names the same parts once. A new rig made of the same devices in a new combination needs no new hardware code. This page lists each include: what it takes, what it gives and where it lives.

## The rig model and its parts

`open_rigs.rigs.lab_rig.LabRig` (`src/open_rigs/rigs/lab_rig.py`) is the whole of a rig's `rig.yml`. Every part is optional: a rig's file lists the parts it has, each workflow takes the ones it drives, and a name a workflow asks for and does not find stops it at Start. `uv run regenerate-lab-rig` here writes its schema (`src/open_rigs/schemas/lab_rig.json`) and generates its C# into OpenRigs.Devices (`OpenRigs.Devices.Rigs`: `LabRig`, `DeserializeFromYaml`, `SerializeToJson`), which every lab workflow reads `rig.yml` with, so no workflow generates or keeps its own; `src/open_rigs/rigs/rig-template.yml` is the lab's one template, which a new rig's `rig.yml` is copied from. The parts are in `src/open_rigs/components/`:

| Part | `rig.yml` key | Module |
|---|---|---|
| Harp Behavior boards (`BehaviorBoard`, its `wiring` and `liveView`) | `behaviorBoard` | `harp_boards`, `wiring`, `live_view` |
| Timestamp generators | `timestampGeneratorGen3` | `open_rigs.devices` |
| Stepper drivers of a lick spout stage (`HarpStepperDriver`, its `wiring`) and the stage's default position | `stepperDriver`, `lickSpoutDefaultPosition` | `harp_boards`, `wiring` |
| Lick detectors | `licketySplit` | `open_rigs.devices` |
| Cameras (`SpinnakerCamera`: serial, exposure, gain, binning, `pixelFormat`, blank keeping the camera's stored format) and the machine's `VideoEncoder` | `camera`, `videoEncoder` | `video` |
| A projector's mesh map and gamma table | `projectionCalibration` | `calibration` |
| Speakers, every one equalised, and the penalty sound's channel (`EqualisedSpeakerArray`) | `speakerArray` | `speakers` |
| Zapit (`ZapitServer`) | `zapit` | `zapit` |

Reward valves and the Zapit trigger are found from the Behavior board's `wiring`:

```yaml
behaviorBoard:
  main:
    portName: COM3
    usbSerial: AB0M7PLB
    pulseController:
      outputPulseEnable: "DO1, DO2"
      outputs:
        DO1: { discriminatorType: CalibratedPulse, artefact: calibration/valve-DO1.json }
        DO2: { discriminatorType: CalibratedPulse, artefact: calibration/valve-DO2.json }
        DO3: { discriminatorType: FixedPulse, pulseWidthMs: 0 }
    wiring:
      DO0: { device: CameraTrigger, targets: [Camera-Face, Camera-Pupil, Camera-Body] }
      DO1: { device: RewardValve, side: left }
      DO2: { device: RewardValve, side: right }
      DO3: { device: ZapitTrigger, note: also the masking light }
```

The model refuses a `rig.yml` whose wiring has a `RewardValve` without its `side`, two on one side, or one on a line whose output is not a `CalibratedPulse`; reward valves on more than one board (every reward fires through one board's `TriggerCalibratedPulse`); more than one `ZapitTrigger` on the rig, or one on a line in `outputPulseEnable` (a pulse-enabled line ends itself after its `PulseDOx` width, and the Zapit line, with the masking light on it, is held from the trigger until the workflow clears it; its `outputs` entry stays, a `FixedPulse` of width 0); a `zapit` section with no `ZapitTrigger` line; and a camera that no DO0 or DO1 `CameraTrigger` line names in its `targets` (as `Camera-<Entry>`, the entry capitalised). It refuses any key it does not know, as the generated C# does at Start. Every refusal says what it refuses, "(lab rig model, open_rigs.rigs.lab_rig)", then how to fix it. A speaker array needs `penaltySoundChannel` (beside `device.bootDelaySeconds`, `syncChannel` and `syncGain`) and a filter on every speaker.

## A piece

Each piece is one device instance, named `Kind-Instance` as in the data (`Camera-Face`, `LicketySplit-Left`, `BehaviorBoard-Main`). It takes its entry from `rig.yml` (`RigConfigs`, from `ReadLabRig`) by that `Name`, publishes the entry as the `AsyncSubject` `<Name>`, opens the device behind `<Name>.Data` (a `PublishSubject`) and, for a device that takes commands, `<Name>.Commands` (a `BehaviorSubject`, so a per-trial graph that sends one command and completes leaves it open), and logs itself under `<Name>\` once the experiment folder exists (`PathPrefix`) and, for a Harp device, the Harp clock is set (`HarpClockSet`). Its `Name` is one externalised property, mapped onto every place inside that needs it (`RigDevice`, the subject, its log), so a piece cannot log under one name and open another. `CommandsSubjectName` and `DataSubjectName` stay explicit properties, as Bonsai's XML cannot build a string, and `workflow_lint` holds them equal to `<Name>.Commands` and `<Name>.Data`. A line piece on a Behavior board (`PulseOutputs`, `ZapitTriggerLine`, `RunningWheel`, `ClockFromBoard`, `SpinnakerCamera`, `CameraTriggers`) takes the board's `Name` as `Board`, and the board's subjects it uses, held equal the same way: `PulseOutputs`, `RunningWheel`, `ClockFromBoard` and `CameraTriggers` take `BoardCommandsSubjectName` and `BoardDataSubjectName`; `SpinnakerCamera` takes only `BoardDataSubjectName` (it has no commands property); `ZapitTriggerLine` takes only `Board`, `ManualPulses` `Board` and `BoardCommandsSubjectName`, and `CameraLiveControls` `Board` and `Camera`. A piece's `Name` starts with its kind (`BehaviorBoard-`, `Camera-`, `LicketySplit-`, `TimestampGeneratorGen3-`): `RigDevice` finds the entry by the instance alone in the piece's own `rig.yml` group. A piece's other inputs (`CamerasExpected`, `WheelDistanceSubjectName`, `Binning`, ...) are its own properties. `DomeHardware` and `BehaviorBoxHardware` are the worked examples of a rig list. Every name defaults empty or `UNMAPPED`, never a real subject's name, so an unset one fails the build naming no other device's subject. A piece that needs to be ready before Go announces its stage into `ReadyStages` through Core's `AnnounceStage`, which never completes (a source that completed into the `ReplaySubject` would close it for every other piece). A piece missing from `rig.yml` stops the workflow at Start, naming the entries there are.

`rig.yml` configures pieces; it never adds or removes one. A workflow's graph is fixed in its XML, so a rig lacking a device its workflow includes cannot run it.

| Include | File | Takes | Gives |
|---|---|---|---|
| `ReadLabRig` | `OpenRigs.Devices:ReadLabRig.bonsai` | property `ConfigRoot` (no default: unset, the workflow stops at Start naming it) | this machine's `rig.yml` (`<ConfigRoot>\<MACHINE>\rig.yml`), read once into `LabRig`: `ConfigRoot`, `RigConfigDirectory`, `RigFile` and `RigConfigs`, each an `AsyncSubject`, the `LabRig` also as its output. | `ReadyGate` | `OpenRigs.Devices:ReadyGate.bonsai` | properties `PieceStages` (the pieces' stages) and `WorkflowStages` (the workflow's own, empty by default) | declares `HarpClockSet` and `ReadyStages`; reports `Ready` (OpenRigs.Control `ReportPhase`) once every stage in `PieceStages` and `WorkflowStages` has come, then publishes `Ready`, the `AsyncSubject` a task waits on; stops naming what never came after 180 s (`StartupWatchdog`). | `ClockFromTimestampGenerator` | `OpenRigs.Devices:ClockFromTimestampGenerator.bonsai` | `Name` (`TimestampGeneratorGen3-<Entry>`), `timestampGeneratorGen3.<entry>` | the generator as a piece (opened, logged); its clock set to UTC, the write re-sent each heartbeat until one agrees (`SetHarpClock`); `Timestamp` and `HarpClockSet`, announced as `HarpClockSet`. | `ClockFromBoard` | `OpenRigs.Devices:BehaviorBoard.ClockFromBoard.bonsai` | `Board`, `SetClock` (true by default) | the same from a Behavior board's own clock, for a rig without a timestamp generator (a write is lost about one start in four, hence the re-send); Timestamp is the time of the board's AnalogData events (1 kHz), HarpClockSet is checked on its 1 Hz heartbeat; also announces `HarpClockRead` at the first heartbeat. `SetClock` false reads the board's time without ever writing it, for the valve calibration on every rig (on a rig with a timestamp generator the board follows the generator, on one without it runs on its own; the pulses are timed only against each other): `PieceStages` names `HarpClockRead` in place of `HarpClockSet`, only the 30 s and 3 s heartbeat stops remain, and only a `NoExperimentFolder` workflow may use it |
| `CameraTriggers` | `OpenRigs.Devices:CameraTriggers.bonsai` | `Board`, `CamerasExpected` | the board's `CameraTriggerController` with `rig.yml`'s `cameraTriggerController`; `StartCameras` once every camera in `CamerasExpected` has begun acquiring (`CamerasOpen`), as a camera drops a trigger that comes before; stops naming the cameras that never opened after 60 s. The triggers are never stopped (no piece sends the controller's `StopCameras`): a Stop ends the workflow at once |

A workflow has exactly one clock. Order in the workflow: `ReadLabRig`, `ReadyGate`, then the clock and pieces in any order. Keep `ReadLabRig` where nothing it reads is defined later, ahead of the group that holds the pieces. The C# lookups by name (`ExperimentManifest`, `RecordHarpDevices`, `StreamDevices`) come after the pieces.

## The rig list

`DomeHardware` (`OpenRigs.Devices:DomeHardware.bonsai`) is the hardware of every rig of its kind: `ReadyGate`, `ClockFromTimestampGenerator` (`TimestampGeneratorGen3-Main`), `BehaviorBoard-Main` with `PulseOutputs`, `ZapitTriggerLine` and `RunningWheel` (`WheelDistanceCm`), `LicketySplit-Left` and `-Right` (`LickStateLeft`, `LickStateRight`), `LickSpoutStage`, `Camera-Face`, `Camera-Pupil`, `Camera-Body`, `CameraTriggers`, `SpeakerMixer` and `ProjectorDisplay` (from `rig.yml`'s `projectionCalibration`): every task on these rigs has background noise and a screen. Its `ReadyGate` waits for every stage these announce, `MixerStarted` included. It exposes `DisplayDevice` and `WorkflowStages` (its `ReadyGate`'s). It holds no `ReadLabRig`: the workflow includes that once, before it, as a piece's log waits for `PathPrefix`, whose `LogLabExperiment` reads `RigConfigs`, so `RigConfigs` defined inside the rig list would be defined in terms of itself (`hardware_problems` refuses a `ReadLabRig` after `ReadyGate`). Every rig of that kind has these devices under these names. A task on it makes its own sounds and stimuli (multicast into the mixer's subjects, drawn on `DrawStimuli`) and includes neither again (`hardware_problems`); Zapit is the task's.

`BehaviorBoxHardware` (`OpenRigs.Devices:BehaviorBoxHardware.bonsai`) is the behaviour boxes' hardware: `ReadyGate` (waiting for `HarpClockSet` and `Camera-Overhead`), `BehaviorBoard-Main` with its own clock (`ClockFromBoard`) and `RunningWheel` (`WheelDistanceCm`), and `Camera-Overhead` on `CameraTriggers`. It exposes `Binning`, the camera's in place of `rig.yml`'s while set, and `WorkflowStages` (its `ReadyGate`'s). `CameraLiveControls`, optional, stays in the task that wants it.

A workflow that runs on several rig kinds is one thin entry file per kind and one shared include of its own: each entry (`src\<kind>.bonsai`) holds only its launch properties, `Initialization` (`ExperimentControl`), its kind's rig list and the shared include (such as `src\Extensions\Job.bonsai`), which holds the job, with `LiveView` its last top-level node. A stage the job announces itself (a valve calibration's `CalibrationReady`) is the entry's `WorkflowStages` on its rig list, which passes it to `ReadyGate`. `workflow_lint` reads each own include as the workflow (`Workflow` puts its nodes inside the include node), opening its `Path` as Bonsai 2.9 does: from the launched workflow's folder (`src`, Bonsai's working directory), never from the including file's, `.bonsai` added to a `Path` with none; an own include Bonsai would not find stops the lint naming it.

## Task-side includes

These hold what every task does the same way, but stay in the task: their inputs or files are the task's. A task includes `LaunchSettings`, `TrainingStage`, `LogLabExperiment`, `BackgroundNoise` and `PlayPenaltySound` (with sound), `TaskLogs`, `LogRngSeed`, `Rewards` (with reward valves) and `ExperimentRecords` once each; `LogControlEvents` is inside `ExperimentRecords`, `ManualRewards` and `DeliverReward` inside `Rewards`, `LogTrial` and `Zapit.ZapitLogs` inside `TaskLogs`. Reading the task file stays in each task, as its type is the task's.

`LogLabExperiment` is a top-level node of its own, after `ReadLabRig` and the node that publishes `RunSettings`, and before the hardware: every device's log waits for its `PathPrefix`, and Bonsai builds a subject's whole top-level node when a subscriber comes first, so inside a group that reads `Timestamp`, or after the pieces, it is defined in terms of itself (`experiment_log_problems`). The task keeps its task file and its own logs beside `TaskLogs`, then `ExperimentRecords` last. `ConfigRoot` is stated in three places a workflow cannot share: `ReadLabRig`'s, `ExperimentRecords`' and `StreamDevices`', as `RecordHarpDevices` and `StreamDevices` read `rig.yml` when the workflow is built, before any subject has a value, and no edge may feed `StreamDevices`; `check-workflow.ps1` holds the three to one root.

### A workflow with no experiment folder

A calibration or a preflight drives the same pieces but makes no experiment folder. It includes `NoExperimentFolder` (`OpenRigs.Logging:NoExperimentFolder.bonsai`) once, in place of both `LaunchSettings` and `LogLabExperiment`. It takes the property `SubjectId`, a name that is no mouse's (such as `_valve-calibration_`), and gives what the pieces read from an experiment: `PathPrefix`, declared and never published, so no piece's log starts and nothing is written under `rig.yml`'s `rootPath`; and `SubjectId` from Start, so `LickSpoutStage`'s in positions are `rig.yml`'s `lickSpoutDefaultPosition` and `SaveSpoutPositions` writes no mouse's file. The workflow writes only its own files (a calibration's results beside `rig.yml`). `no_experiment_folder_problems` holds every workflow to one of `LogLabExperiment` and `NoExperimentFolder`, once, and refuses its own stand-ins: a `PathPrefix` it declares or publishes, and, with `NoExperimentFolder`, `LaunchSettings` or a `SubjectId` of its own, in its own included files too.

### A preflight

A preflight checks every device a rig's `rig.yml` declares before training, one workflow per rig kind: its rig list, `NoExperimentFolder`, and `PreflightChecks` (`OpenRigs.Devices:PreflightChecks.bonsai`), the check every kind shares, with no device code of its own. Its rows are `rig.yml`'s devices (`PreflightDevices`, in the order `behaviorBoard`, `timestampGeneratorGen3`, `stepperDriver`, `licketySplit`, `camera`, `speakerArray`, `projectionCalibration`), so a device `rig.yml` has and the rig list lacks still has a row, an error. The workflow taps each piece's `<Name>.Data` (`PreflightTap`, multicast into `DeviceTicks`, which `PreflightChecks` declares): a tick per item, counted each second; a device that has sent nothing 5 s after start has its error until its first item (`DeviceReports`) into the `devices` metric (`DeviceRates`). A fault beyond presence (a port another program holds, a camera that sends no frame, a clock never set) stops the preflight at Start naming the device, as the piece stops a task. At Go `PreflightChecks` reads its property `TaskPath`, the rig kind's task file (`ReadPreflightTask`: `countSeconds`, 1 to 60, and `questions` by `rig.yml` kind; any other key is refused), counts each device in turn (`step` metric), asks each question in turn (`prompt` metric) until the controller's `Confirm` (`PreflightChecks` declares it, and passes each on `Confirms` for the workflow's own use, such as playing a test sound until it is answered), writes the rows (`device,measure,value,detail`) to its property `RawFile` and reports `Finished`. A speaker array has no count: the workflow multicasts the test sounds it sent into `SpeakerSounds`, given before the person's answer.

A piece declares its own commands and parameters with OpenRigs.Control's `DeclareControls` (`Piece`, `Parameters`, `Commands`, as `ExperimentControl`'s): `ControlServer` gathers every piece's subscribed before or after it, so `status` lists them with the piece's name (`piece`, empty for the task's own) and a name declared twice (a task's copy, a piece included twice) stops the workflow at Start naming both. A piece the workflow does not include, or that does not run on this rig (a stage behind a condition that finds none in rig.yml), declares nothing. `ExperimentControl`'s `Parameters` and `Commands` are the task's own. `workflow_lint.control_declarations` reads both inside every include it can (a declaring piece is in `SIGNATURES`), held by `undeclared_commands`, `declared_twice` and `spout_step_size_problems`. A piece included once per device declares its controls named from the device with `DeclareDeviceControls` (`Name` the device, the piece; each parameter and command `<Name>.<its name>`), and reads them with `OnDeviceParameterSet`, `DeviceParameterDefault` and `DeviceParameterMaximum` (`Name`, `Parameter`), so one externalized `Name` names the device, its subjects and its controls: `CameraLiveControls` declares `<Camera>.ExposureUs` and `<Camera>.GainDb`, and `workflow_lint` (`DEVICE_DECLARERS`) reads them per include and refuses two on one camera. OpenRigs.Control's `EndAfterStop` (beside `ExperimentControl`) ends headless Bonsai when it is still running `GraceSeconds` (2) after the controller's stop, exit code 0, or after the workflow began to end with no stop, an error, exit code 1 (headless Bonsai exits 0 after an error); nothing in the editor. `ExperimentManifest`'s `ConfigFiles` defaults to `{RigFiles}`: `rig.yml` under the launch's `ConfigRoot`, every path-like value in it, and the mouse's spout positions on a rig with `lickSpoutDefaultPosition`.

## Ready

`ReadyGate` reports `Ready`, which lets the operator press Go, once every stage in its `PieceStages` and `WorkflowStages` has come into `ReadyStages`. `PieceStages` is the stages the workflow's pieces announce: `HarpClockSet` (the clock; `HarpClockRead` for a `ClockFromBoard` with `SetClock` false), `SpoutsHomed` (`LickSpoutStage`), each camera's `Name` at its first frame, and `MixerStarted` (`SpeakerMixer`, at least 3 s after Start), so every sound a task sends from Ready on is played. A workflow that needs more before Go announces a stage of its own (an `AnnounceStage` into `ReadyStages`) and names it in `WorkflowStages`: the valve calibration's `CalibrationReady` (its pulse setup out and the spouts in), the projector calibration's `PhotodiodeReading` (the first ADC0 reading). `workflow_lint.hardware_problems` holds `PieceStages` equal to the stages the workflow's pieces announce and `WorkflowStages` to those the workflow announces itself, and refuses any multicast into `ReadyStages` not fed by one `AnnounceStage`, reading the workflow's own included files (`src\Extensions`) as the workflow. A piece behind a per-element operator (a `SelectMany` that runs it only on a rig whose `rig.yml` has its device, as the valve calibration's lick spout stage) may never announce, so `PieceStages` leaves its stage out and the workflow waits with a stage of its own. `CheckMixerStarted` stays the safety net: a stimulus or penalty sound that still reaches the mixer before it has started stops the workflow.

## Sound

Every sound a task plays goes through `OpenRigs.Audio` ([Speakers and Sounds](../bonsai-operators/OpenRigs.Audio/speakers.md)). `SpeakerMixer` loads the speakers (`Speakers`) and starts the mixer; a task makes each sound's buffer and multicasts it into the mixer's subject for it. `SpeakerBuffer` lays a sound (or a table of sounds) out on chosen speakers, equalised for each (a stimulus) or not (a background noise); its `SyncCopy` adds a stimulus's sync copy (`syncGain` on `syncChannel` for the sound's length), so acquisition sees when every stimulus plays; `PenaltySoundBuffer` gives the lab's one penalty sound on `penaltySoundChannel` alone, so a task file names no penalty sound file; `BackgroundNoise` plays the lab's one background noise, the file `rig.yml`'s `speakerArray.backgroundNoise` names (the server's `config\shared\sounds\background_noise.wav`, copied to each rig by its upkeep), so no task keeps a noise file.

Every sound plays at a level, never a gain: `levelDbfs` in the task file, in dBFS RMS, the RMS of the sound over its whole length as the task gives it (before equalisation) against full scale, so a full-scale sine is -3 dBFS (`SoundLevel`). Each request carries its own level, mapped onto `SpeakerBuffer`'s or `PenaltySoundBuffer`'s `LevelDbfs`, so any sound can change trial by trial; a level that varies by trial is a trial column (such as `audioLevelDbfs`), a fixed one stays in the saved task file. `open_rigs.core.task` holds the task file's blocks (`StimulusSound`, `RewardTone`, `BackgroundNoise`, `PenaltySound`) and the lab's defaults, the same as `SoundLevel`'s: stimuli -30, penalty -30, reward tone -36, background -50. They are defaults only: each task file states its levels. A buffer whose peak reaches -1 dBFS after equalisation stops the workflow, naming the sound and how far to lower it; build each buffer once the task file is read at Go, so the check comes before trial 1. No task scales a sound itself. The levels become dB SPL once each speaker is calibrated for loudness.

## The trial loop

Every task runs its trials on `TrialLoop` (OpenRigs.Devices), so the trial start, the laser's lead and trigger, the response window and the interval are timed one way in every task ([Trial Loop](../bonsai-operators/OpenRigs.Devices/trial-loop.md)). A trial: drawn at its interval's start (the last outcome plus its timeout; trial 1 the first tick); a hardware-triggered Zapit armed during the interval once the last laser is done; the start at the interval's end less the lead, `max(laserToStimulusSeconds, 0)`, or later until the quiet waits hold (`QuietWait`); the trigger `laserToStimulusSeconds` before the stimulus, stopping the workflow if Zapit has not armed the trial by then (naming the last laser when it held Zapit past the trigger, or freed it less than the 0.2 s reply margin before it; without hardware triggering, a trigger before the last laser frees Zapit stops it the same way), and never on a trial already answered; the stimulus the lead after the start; the response window `ResponseDelaySeconds` after the stimulus for `ResponseWindowSeconds`; the outcome, then its timeout. The task supplies the rest as an `ITrialRules`: the draw (given the last outcome), each trial's `TrialTiming` (`ItiSeconds`, lead, quiet waits, laser, response window, `TrialCue`s: from the stimulus or the next interval's start (`CueAnchor.Stimulus`, `NextIti`), a stimulus cue `droppedAtOutcome` never coming once the trial has its outcome, such as the spouts in), and the response rule, called at the start, the stimulus, each tick from the stimulus, each lick, each wheel sample and the window's end, returning the outcome when the trial ends. `LaserTiming.UntilOutcome` keeps the laser on to the outcome (stopped at `LaserCap`) with the trigger line held past it; `LaserTiming.ForDuration` runs it a fixed time from the trigger, the next trial armed after Zapit's ramp-down. A trial is an `ITrial` (its `TrialNumber`), and an `IZapitTrial` (its laser condition, laser on and power) only in a task whose trials are laser trials; an outcome is an `ITrialOutcome` (`PenaltyTimeoutSeconds`). The names are the trial columns': `TrialTimes.ItiStartTime`, `ItiSeconds`, the `Iti` event at the interval's start.

A task's `src\Extensions` declares its rules and a three-line `RunTrials` combinator that returns `TrialLoop.Observe` on its streams; its `TaskLogic` multicasts the events into `TrialEvents` and picks each kind with `PickTrialEvents` to drive the hardware: `Trial` from `Start`, the trigger line from `Trigger` and `TriggerOff`, the trial row, reward and penalty sound from `Outcome`. The row's shared block is filled by `SharedTrialColumns.Fill(row, trial, times, penalised, penaltyTimeoutSeconds, penaltySoundEnabled)` from the loop's `TrialTimes`: `trialNumber`, `itiStartTime`, `itiSeconds`, `quietWaitSeconds` (if the row has it), `trialStartTime`, `stimulusOnsetTime`, `outcomeTime`, `penaltySound`, `penaltyTimeoutSeconds` and the opto block (`laserCondition`, `laserPowerMw` 0 unless the laser was triggered, `laserTriggerTime`), by field name, refusing a row missing or mistyping one; the task fills `trialType`, `outcome`, `rewardSizeUl` and its own columns.

## The trial log

Every task's `schemas\trial-columns.yml` starts with the shared block, in order, with the same types, units and descriptions: the lab's 12 core columns `harpTime, trialNumber, trialType, outcome, itiStartTime, itiSeconds, trialStartTime, stimulusOnsetTime, outcomeTime, rewardSizeUl, penaltySound, penaltyTimeoutSeconds` (`trialType`, `outcome`, `rewardSizeUl` and `penaltySound` described by each task), with each opt-in block the task uses in its place: `quietWait` (`quietWaitSeconds`, after `itiSeconds`) and `opto` (`laserCondition, laserPowerMw, laserTriggerTime`, after `penaltyTimeoutSeconds`). The blocks are `open_rigs.rigs.trials`' `CORE_COLUMNS`, `QUIET_WAIT_COLUMNS` and `OPTO_COLUMNS`; each task's `tests\test_trial_columns.py` holds its file to them with `shared_block_problems(columns, blocks)`, naming the blocks it uses, so change a block there and regenerate every task's file. A task's own columns follow.

Keep a task's outcome logic (what counts as the response, and the reward, penalty sound and spouts that follow) in one C# operator that runs on every tick, the way a corridor task's state machine runs on every position update. Nodes that run only at an outcome pay .NET's first-run compile at trial 1's: in a two-spout task whose choice, row and consequence are a chain of nodes, trial 1's reward came 8 to 20 ms after its outcome and every later one within 2 ms; neither writing the row on its own thread nor compiling the task's C# at Start changed it, and only an earlier outcome through the same nodes did. `summarise-experiment` reports a reward more than 2 ms late.

`uv run summarise-experiment <experiment folder>` (`open_rigs.rigs.trials.summarise`) reads one experiment from its files alone and checks the rows against each other and the task file: trial numbers and outcomes, each trial's start, stimulus and laser trigger within 2 ms of where the task puts it, each interval starting at the last outcome plus its timeout, the penalty sound with each timeout, and a `RewardDelivered` row for each rewarded trial. A log without `quietWaitSeconds` has no quiet waits, and a task file without `optogenetics` no lead. Its performance is Correct / (Correct + Incorrect) over the trials both spouts were offered.

## Video logging

Each `SpinnakerCamera` logs its own video with `OpenRigs.Logging:LogVideoFfmpeg.bonsai` as `<Name>` (`workflow_lint` refuses upstream's `LogVideo` and `LogRawVideo`, kept for upstream merges), at its trigger's frequency, from its first frame once `PathPrefix` exists. Every video and its CSV include the first frame, and a dropped frame is a jump in `frameId` with the triggers around it kept. A frame counter that goes back stops the workflow, naming the camera.

in a task or calibration a valve fires only calibrated pulses, through `DeliverReward` or a calibration's own `FirePulses` on `TriggerCalibratedPulse`, each writing its width before it fires, and only `ManualPulses`, a person's check of a rig, holds one open by hand). `ReadTextFile` (Core) reads a file when its path arrives, such as the task file at Go.
