# The Coen Lab's open-rigs

This fork's `main` is what every Coen Lab workflow runs: upstream open-rigs (branch `rig-config-resolver` at `3788bfb`, NeuroThom's per-machine config operators, and upstream `main` merged at `f313716` on 4 Nov 2026 for the calibration loop av-dome's `tr-open-rigs` uses), plus the lab's fixes and packages. Each lab change is a commit on `main`; a change meant for upstream also gets a branch of its own for its pull request.

## Every lab workflow runs this

A lab workflow is any repository on [rig-setup](https://github.com/Coen-Lab/rig-setup), for any profile, or in [`workflows.txt`](workflows.txt), that is a Bonsai project in the open-rigs layout (`.bonsai\Bonsai.config` and `src\main.bonsai`). `scripts\update-workflows.ps1` keeps each one's `main`, and each branch ticked for it in rig-setup (or named after it in `workflows.txt`). Ticking Leave Main Alone on the repo's right-click menu in rig-setup's Repos, or `!main` in `workflows.txt`, leaves `main` alone, on this repository. A ticked branch gone from GitHub (merged or deleted) is reported `gone`, not failed, until Repos takes the tick off:

- every package in `local_packages\` at the version here, with what it depends on as coen-behaviour-box's `Bonsai.config` has it, and the `../local_packages/` NuGet source;
- open-rigs (Python) from this repository: an `open-rigs` git source in `pyproject.toml` is pinned to the last commit here that changed `src\`, `pyproject.toml` or `local_packages\`, `uv.lock` is relocked, and `regenerate-schemas` is run if the workflow has it, then `examples\rig.py` (its `config\rig-template.yml`) if it has that. The schema and the Bonsai packages then come from the same commit.

A branch that changed is checked with its own `scripts\check-workflow.ps1` (else `scripts\check-bonsai.ps1` here) after its Bonsai setup. If the check passes, what the script wrote is committed and pushed; rig-setup's 30-minute update takes `main` to the rigs. If it fails, nothing is committed and the table at the end names the branch and why; the next run tries again. It works in clones of its own under `%LOCALAPPDATA%\lib-open-rigs\clones`, so nobody's working copy is touched.

It runs after every push with `scripts\push.ps1`, and hourly on PIPOFFICERIG (`scripts\schedule.ps1` registers the task, which runs `scripts\hourly.ps1` from its own clone at `%LOCALAPPDATA%\lib-open-rigs\self`, set to `origin/main` each hour, so a change to the run needs no new registration; log in `%LOCALAPPDATA%\lib-open-rigs\update-workflows.log`, every failed run's kept in `update-workflows-failed.log` beside it, and the latest failed run copied to `K:\config\<MACHINE>\<MACHINE>_WorkflowsFailed.txt`, which the next good run removes). Every run, passed or failed, also writes `K:\config\<MACHINE>\<MACHINE>_WorkflowsUpdate.json` (`machine`, `started`, `finished`, `exitCode`, and `lastPass`, the last run that passed), and rig-setup's rig-status report and Machines window flag it when the last run failed or `finished` is over 3 hours old, and ClaudioVisual's rig health DMs the same failures and a `finished` over 26 hours old: the task runs only while Pip is signed in to PIPOFFICERIG, and Task Scheduler's history reads 0 whatever happened, so this file is how a task that stopped running is seen. A run of `update-workflows.ps1` that does not parse is a failed run (it runs as a child process, as `push.ps1` runs it). It reads rig-setup's repo list at `K:\config\profile-repos.json` (`-RepoList`): rig-setup maps K: only on shared and rig machines, so on PIPOFFICERIG it is mapped by hand. The checks build workflows and run their operators offline, but a workflow that loads `Bonsai.Spinnaker` needs the Spinnaker SDK, so this runs on a lab machine, not in CI.

## Changing a lab package

1. Raise `<Version>` in `src\<Package>\<Package>.csproj`. NuGet caches by id and version on every machine, so `build-package.ps1` refuses a version committed in any ref this clone has, and `push.ps1` fetches and refuses one origin already holds. open-rigs' build stamps `42.42.42-dev0` on a plain build; `build-package.ps1` passes the `.csproj`'s version.
2. Run its tests, a console program that needs only the .NET SDK and exits 0 when every check passes: `dotnet run --project src\OpenRigs.Control.Tests` (likewise `LiveView`, `Manifest`, `HarpDevices`; the patched `Logging` and `Core` have `src\OpenRigs.Logging.Tests` and `src\OpenRigs.Core.Tests`).
3. Build it into `local_packages\`, replacing the old version: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\build-package.ps1 -Package OpenRigs.LiveView`
4. Commit, and push with `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\push.ps1` instead of `git push`. It refuses a raised version with no `.nupkg`, source changed after its `.nupkg`, a `.nupkg` built on other source or already on origin with other contents, two versions of one package, and uncommitted or unparsable `scripts\*.ps1`, then updates every workflow.

Every public type and member of a lab package has a `<summary>`; a missing one stops the build (CS1591 in each `.csproj`). The packages build against Bonsai.Core 2.9.0 with current C#; only a workflow's own `src\Extensions`, which Bonsai compiles, must be C# 5.

Pushing `main` prints "Bypassed rule violations": the org ruleset asks for pull requests, and the lab commits on `main`.
