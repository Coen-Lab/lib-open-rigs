# OpenRigs.Manifest

One node, `ExperimentManifest`, that writes `manifest.json` into each experiment folder: what ran, from which commit, with which settings and configuration, what it had to leave, how the run ended, and every file it left. A workflow drops it in once, after `LogController`; nothing has to be wired to it.

The format is [`FORMAT.md`](FORMAT.md), version 4. This node writes it on a rig; the server's migration converter is its only other writer, for experiments recorded before it. The overnight copy and the server each write their own file beside it (`sync.json`, `ingest.json`). Every manifest names what wrote it (`writer`).

## What It Finds by Itself

| What | From | Without it |
|------|------|------------|
| The experiment folder | the `PathPrefix` subject, OpenRigs.Logging's `LogController` | The workflow does not build: ExperimentManifest says to put it after LogController. |
| Settings at Go | OpenRigs.Control's `ExperimentControl`: subject, session, when Go was taken, and who launched the experiment, sent Go and stopped it, as the controller named them, and the id the controller passed for the launch as `--property:LaunchId` (`launch_id`) (`launched_by`, `go_by`, `stopped_by`: `id` and `name`, or null). The parameters at Go are in the experiment's `Settings\Settings_Experiment_<DateTime>.json` (Control's `ExperimentSettings`), not here. | No `control` section. |
| How the run ended | OpenRigs.Control's phase when the workflow stops: a run that reported `Finished` is `completed`, even when the controller stops it afterwards (a controller may, after every run); a controller stop before that is `stopped`, with the stop's reason (told by the stop's reason, which only the controller's stop sets, not by the phase alone) | `stopped` |
| Launch | Bonsai's command line: every argument, and each `--property:Name=Value` (or `-p:`) by name | |
| Source | the workflow file's repository: origin, branch, commit, whether tracked files differ, and when they do which files and a sha256 of `git diff HEAD` (`changed`, `diff_sha256`) | The editor's File, Open passes no file: the working directory's repository, which Bonsai sets to the workflow's folder. |
| What the experiment must leave | rig.yml (the one in `ConfigFiles`) and the subjects the workflow publishes, as `StreamDevices` finds devices: each device entry (`camera: overhead:`, named `Camera-Overhead`) whose subject is published before this node, as `Camera-Overhead` or `Camera-Overhead.Data`, must leave a folder `Camera-Overhead/` with at least one file, which is where OpenRigs.Logging logs it. With `harp` in `ExpectedFiles`, each Harp device (a `portName` in rig.yml that is not `null`, `BehaviorBoard-Main.Data` published as `HarpMessage`: `src\Shared\HarpRig.cs`, the rule `RecordHarpDevices` uses) must also leave the files OpenRigs.HarpDevices' `RecordHarpDevices` writes, `BehaviorBoard-Main/BehaviorBoard-Main_device.json` and, when a Harp package loaded in the workflow has the kind's WhoAmI, `BehaviorBoard-Main/BehaviorBoard-Main.yml`, which do not count towards the folder's own file | A note naming each device not expected, and each register map not expected, and why. |

## Expected Files

`files` lists what is in the folder when the run ends, so a device that never wrote anything is simply absent from it. `expected` says what had to be there: each entry with its path, why it is expected, its `condition` and whether it was `required` at that write, and `found`, the number of files matching it at that write. The overnight copy refuses to copy a `completed` experiment whose required entry left no file, and raises an alarm naming it, as it does for a listed file that has gone; a run that ended any other way is copied without what it never wrote, named in `sync.json`'s `unmet` and a note, with an alarm.
## Settings

| Property | Default | |
|----------|---------|-|
| `ConfigRoot` | none | The root under which each machine has its own `<MACHINE-NAME>\rig.yml`, which `ConfigFiles`' `{RigFiles}` reads; OpenRigs.Logging's `ExperimentRecords` maps the workflow's onto it. Unset with `{RigFiles}` in `ConfigFiles`, the workflow stops at Start. |
| `ConfigFiles` | `{RigFiles}` | The configuration files the workflow runs with, separated by `;`. Each is read **once, at Start**, and named in the manifest by its path and sha256, so the manifest says which file ran even if it is edited during the run. Environment variables are expanded; a relative path is from the workflow's repository (`schemas\session.yml`). A missing file is noted, not an error; the note names the path as looked for, environment variables and `{SubjectId}` filled in (with no `SubjectId` on the command line, the token stays and the note says so). It cannot follow a `--property:ConfigRoot` given at launch; when the rig.yml here is not under that ConfigRoot, a note says so. |
| `ExpectedFiles` | `auto` | What the experiment must leave, separated by `;`: a path in the experiment folder, a folder ending in `/`. `auto` stands for each device's folder, found as above; `harp` for each Harp device's record and register map, for a workflow with `RecordHarpDevices` (a word, not found from that node: Bonsai may build `ExperimentManifest` first, whatever their order in the workflow); `auto;events.csv` adds a file; blank expects nothing. Name each log by the start of its path (`WorkflowData/WorkflowData_Trials_`, `WorkflowData/WorkflowData_Events_`), not its folder: a folder entry is met by any one file in it, so one log could stop and the folder still read found. `path?Subject` is required only while `Subject`, a bool subject the workflow publishes before this node, is true (`Settings/Settings_Laser_?Optogenetics`); the manifest records the entry's `condition` and whether it was `required` at that write (version 4). A condition that is not a bool subject makes its entries required always, with a note; one whose subject has sent nothing leaves them not required, with a note. No wildcards: an entry holding `*` is left out, with a note. A leading `./` is dropped, and an entry that is rooted or holds `..` is left out with a note: it is not in the experiment folder. |
| `TrialColumns` | blank | The workflow's trial columns file (`schemas\trial-columns.yml`): what each `WorkflowData_Trials` column means, its type and, where they apply, its codes and unit. Read **once, at Start**, and copied into the manifest as `trial_columns` with its sha256, so each experiment carries the meaning of its own trial log (FORMAT.md). A relative path is from the workflow's repository. Blank for a workflow that logs no trials. A missing or unreadable file, or a column without a type of `int`, `double`, `bool` or `string`, or two names differing only in case, is noted, not an error. An unquoted `~`, `null`, `Null`, `NULL` or empty value is JSON `null`. |
| `StreamColumns` | blank | Each further `WorkflowData` log's columns file, as `Log=path` entries separated by `;` (`WorkflowData_StimulusState=schemas\stimulus-state-columns.yml`), read once at Start and copied into the manifest as `stream_columns`, by log, as `TrialColumns` is. An entry that is not `Log=path`, or two logs whose names differ only in case, stops the workflow at Start. |
| `IngestScript` | blank | The server's ingest script for this kind of data, as the server's registry names it. |

## The Optional Input: the Run

A sequence connected to it is the run: its completion is `completed`, its error is `error` with the error's message (an error after the workflow's Finished or the controller's stop is `completed` or `stopped`: it is how the workflow stopped), and its elements are counted as `run.items`. Connect one when the run's end is something the controller's phase does not see, such as a Watchdog error on the frames being recorded: the node cannot see an error raised elsewhere in the workflow. Without one, a workflow under ExperimentControl that stops in any other way (an error elsewhere, the editor's Stop) is recorded as `ended-early`, with a note that Bonsai's output has the cause.

## When It Writes

1. When `PathPrefix` names the folder: `run.outcome running`, `run.final false`. It makes the folder if no logger has yet. A write that fails stops the workflow with that error, as any node's error does: an experiment with no record is the thing to stop for. (Thrown back up the thread that named the folder, ControlServer's after Go, the error would close Bonsai with nothing finished.)
2. When the workflow's Finished or the controller's stop comes, the run still going (looked for every 0.25 s): the outcome so far, `completed` or `stopped` (with `run.stop_reason` and `control.stopped_by`), and `run.final false`. A controller may kill a workflow that has not stopped by its deadline, and the end-of-run write then never comes, so the outcome is written here first. A controller keeps an editor's Bonsai open while the manifest says `running` or `run.final false`, and the overnight copy treats `run.final false` as `running` until it is stale; a manifest with no `run.final` is final.
3. When the run ends (the input completes or fails, or the workflow stops): the outcome, `run.final true`, the time, and every file then in the folder (not another writer's `.tmp`, a file deleted while it is listed, `sync.json` or `ingest.json`). A run that fails before the folder exists has no experiment to record: its error ends the node at once (held until the folder appeared, a run that failed at Ready would leave the workflow standing, and a Go then make a folder for it); a run that completes before the folder still waits for it.

Each write is `manifest.json.<pid>.tmp`, then a rename over the old one, so no reader sees half a file or none. Windows refuses the rename while a reader holds the file without delete sharing (Python's `open()`; a controller polls `manifest.json` every second), so it is tried up to 10 times, 50 ms apart, before the write fails; a final write that fails is written to Bonsai's console (stderr) as well as the trace. A workflow stopped before `PathPrefix` (ready mode, no Go) writes nothing: nothing was recorded.

## Things to Know

- **After LogController.** Bonsai knows only the subjects built before a node, so `ExperimentManifest` goes after the node holding `LogController`, at the same level or inside it.
- **Its settings live inside it**, in a `ExperimentManifestSettings` node, as `StreamDevices`' do: Bonsai copies a group when the editor opens a workflow and keeps only its inner workflow. Set them on `ExperimentManifest`.
- **Bonsai internals.** Finding `PathPrefix` asks Bonsai's internal build context by reflection, as Bonsai's own `SubscribeSubject` does (written against Bonsai.Core 2.9.0).

## Needs

`Bonsai.Core` and `YamlDotNet`, and in the workflow `OpenRigs.Logging`'s `LogController`. Not `OpenRigs.Control`: when the workflow has ExperimentControl, the manifest reads its experiment (`ControlState.Current`) by name, so a workflow can have the manifest without the controller's package. The tests run against the real `ControlState` and fail if a member it reads is renamed there.

## Tested

`dotnet run --project src\OpenRigs.Manifest.Tests` runs the writer, the recorder and the editor's copy of the node against a temporary folder, with no hardware and no Bonsai editor: exit 0 when every check passes. It also builds each manifest in [`fixtures/manifest/v4/`](../../fixtures/manifest/v4/) from fixed inputs and compares it byte for byte with the file there; readers in other repositories test themselves on those files. `-- --write-fixtures` rewrites them after a deliberate change to the format.
